📄 Step 1 — Export your Windows Security events

This tool reads CSV or delimited text exports of Windows event logs. It does not read raw .evtx files in this version.

Option A — Windows Event Viewer (point and click)
  1. Open Event Viewer (press Win + R, type eventvwr.msc, press Enter).
  2. In the left pane expand Windows Logs, then click Security.
  3. Optional: use Filter Current Log… on the right to narrow the events, for example Event IDs 4624,4625,4720,4726,4728,4732,1102.
  4. On the right, click Save All Events As… (or Save Filtered Log File As…).
  5. Choose Comma Separated Values (*.csv) if your build offers it. If it only offers Text (Tab delimited) (*.txt), that is fine — this tool auto-detects tab-separated files too.
  6. Upload the saved file below. Do not open and re-save it in Excel first: Excel can damage the quoting and reformat the timestamps.

Honest note: not every Windows 10/11 build shows a CSV option in that dialog. If yours does not, use Option B, which always works.

Option B — PowerShell (most reliable, recommended)

Run an elevated PowerShell (right-click → Run as Administrator), because reading the Security log requires administrator rights. 

# Export selected Windows Security events to CSV for triage practice.
# Run in an ELEVATED PowerShell window. Change the output path if you like.
$ids = 4624,4625,4720,4726,4728,4732,1102,4688
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=$ids} |
  Select-Object TimeCreated, Id, LevelDisplayName, ProviderName, TaskDisplayName,
                KeywordsDisplayNames, Message |
  Export-Csv -Path "$env:USERPROFILE\Desktop\security-triage.csv" -NoTypeInformation -Encoding UTF8

Tip: add ; StartTime=(Get-Date).AddDays(-1) inside the filter hashtable to export only the last day, and keep test exports small while you are learning.

          🧠 How to Think Like a SOC Analyst

          A Security Operations Centre (SOC) is the team that watches an organisation's systems for suspicious activity. "Triage" is the first, fastest pass: deciding which alerts deserve a human's attention, and in what order. This is the workflow they follow.

          1. Identify the event. What is it? Event ID 4625 means a logon attempt failed.
          2. Understand what happened. Read the details: which account, from where, at what time.
          3. Identify the affected user or system. Is this an ordinary user, an administrator, a service account, or a machine account?
          4. Decide whether the activity is expected. Is it normal for this account, this hour, this device? You often cannot know from the log alone — so say so, rather than guessing.
          5. Look for related events. Was there a logoff, a new process, a privilege change around the same time?
          6. Correlate authentication and privilege activity. Failed logons that are followed by a success tell a different story than failures on their own.
          7. Gather additional evidence. Endpoint logs, VPN records, badge access, ticket history, the user themselves.
          8. Decide whether escalation is required. Document what you saw, what you ruled out, and what remains open.

          "One security event rarely tells the entire story. Analysts build context by correlating multiple events."

          "A detection is a reason to investigate, not proof that an attacker is present."

          📚 Windows Event ID reference for beginners

          Windows has thousands of Event IDs. These are the ten worth knowing first for authentication, account and privilege activity. All of them are explained in plain English, and none of them proves that anything bad has happened.

          Windows Event IDs supported by this tool, with plain-English explanations
          Event ID What it records Why an analyst cares
          4624 Successful logon Context, not a warning. It matters when it follows a burst of failures, or happens on a machine or account that should not be logging in.
          4625 Failed logon One is routine. A pattern is interesting: a wrong password, a stale service credential, or somebody guessing.
          4688 Process created Shows what ran. Only recorded if process-creation auditing is switched on, so absence proves nothing.
          4720 User account created Normal for administrators. Worth verifying, because attackers also create accounts to keep access.
          4726 User account deleted Usually tidy administration; occasionally a sign of somebody covering their tracks.
          4728 Member added to a global security group Becomes important when the group is privileged, such as Domain Admins.
          4732 Member added to a local security group The same idea locally — for example adding an account to local Administrators.
          1102 Security audit log cleared Can be legitimate maintenance, but it also removes evidence, so it is normally investigated.
          4104 PowerShell script block logging Visibility into PowerShell commands, which is genuinely useful for both admins and attackers.
          7045 Service installed Often ordinary software installation; also a classic way to make malware start automatically.

          ⚠ What this tool cannot do

          Knowing the limits of a tool is part of being a good analyst. This is a learning aid, not a security product.

          • An event is not proof. Every finding here is a reason to look further, never a verdict.
          • Absence of evidence is not evidence of absence. If process-creation or PowerShell auditing was switched off, those events simply do not exist in the export.
          • CSV exports differ between machines. Column names, date formats and encodings vary with Windows version and regional settings.
          • Not every event carries a source IP. Local and console logons legitimately have none.
          • No baselining. The tool cannot know whether a login is normal for you; only a human with context can decide that.
          • No cross-system correlation. It sees only the file you give it, so it cannot link activity across several computers.
          • Timestamps can be ambiguous. Where a file does not make day/month order clear, the tool says so and disables time-window rules rather than guessing.
          • It is not an EDR, SIEM or SOC platform, and does not replace one.
