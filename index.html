                  How to think like a SOC analyst

                  A Security Operations Centre watches an organisation's systems. Triage is the first pass: deciding which alerts deserve a human's attention, and in what order.

                  1. Identify the event. What is it? Event ID 4625 means a logon attempt failed.
                  2. Understand what happened. Which account, from where, at what time.
                  3. Identify the affected user or system. An ordinary user, an administrator, a service account or a machine account?
                  4. Decide whether the activity is expected. Is it normal for this account, this hour, this device? You often cannot know from the log alone, so say so rather than guessing.
                  5. Look for related events. Was there a logoff, a new process or a privilege change around the same time?
                  6. Correlate authentication and privilege activity. Failures followed by a success tell a different story than failures alone.
                  7. Gather additional evidence. Endpoint logs, VPN records, badge access, ticket history, the user themselves.
                  8. Decide whether escalation is required. Document what you saw, what you ruled out, and what remains open.

                  "One security event rarely tells the entire story. Analysts build context by correlating multiple events."

                  "A detection is a reason to investigate, not proof that an attacker is present."

                  Event ID reference for beginners

                  Windows has thousands of Event IDs. These are the ten worth knowing first for authentication, account and privilege activity. None of them proves that anything bad has happened.

                  Windows Event IDs supported by this tool, with plain-English explanations
                  ID What it records Why an analyst cares
                  4624 Successful logon Context, not a warning. It matters when it follows a burst of failures, or happens on a machine or account that should not be logging in.
                  4625 Failed logon One is routine. A pattern is interesting: a wrong password, a stale service credential, or somebody guessing.
                  4688 Process created Shows what ran. Only recorded if process-creation auditing is switched on, so absence proves nothing.
                  4720 User account created Normal for administrators. Worth verifying, because attackers also create accounts to keep access.
                  4726 User account deleted Usually tidy administration; occasionally a sign of somebody covering their tracks.
                  4728 Member added to a global security group Becomes important when the group is privileged, such as Domain Admins.
                  4732 Member added to a local security group The same idea locally — for example adding an account to local Administrators.
                  1102 Security audit log cleared Can be legitimate maintenance, but it also removes evidence, so it is normally investigated.
                  4104 PowerShell script block logging Visibility into PowerShell commands, which is genuinely useful for both admins and attackers.
                  7045 Service installed Often ordinary software installation; also a classic way to make malware start automatically.

                  Export Windows event data

                  This tool reads CSV or delimited text. It does not read raw .evtx files in this version.

                  A

                  Windows Event Viewer

                  1. Open Event Viewer (Win+R, type eventvwr.msc).
                  2. Expand Windows Logs → Security.
                  3. Optional: Filter Current Log… for IDs 4624,4625,4720,4726,4728,4732,1102,4688.
                  4. Right-click the log → Save All Events As….
                  5. Choose Comma Separated Values (*.csv) if your build offers it.

                  Not every Windows 10/11 build offers CSV in that dialog. A tab-delimited .txt export works too — the tool detects tabs automatically. If neither is offered, use option B.

                  B

                  PowerShell (always works)

                  Run PowerShell as Administrator — reading the Security log requires it.

                  $ids = 4624,4625,4720,4726,4728,4732,1102,4688
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=$ids} |
  Select-Object TimeCreated, Id, LevelDisplayName, ProviderName,
                TaskDisplayName, KeywordsDisplayNames, Message |
  Export-Csv -Path "$env:USERPROFILE\Desktop\security-triage.csv" `
             -NoTypeInformation -Encoding UTF8

                  Add ; StartTime=(Get-Date).AddDays(-1) inside the filter to export only the last day. Event 7045 (services) lives in the System log, so export that separately.

                  C

                  Then upload it

                  Go to Dashboard and drop the file on the upload area. Do not open and re-save it in Excel first: Excel rewrites quoting and dates and can break the file.

                  Privacy

                  Your Windows security logs are analysed locally in your browser. Files are not uploaded or transmitted anywhere.

                  No upload

                  The only file API used is FileReader, which hands the bytes to the page. There is no upload endpoint, because there is no server.

                  No network calls

                  No fetch, XMLHttpRequest, WebSocket or beacon anywhere in the code. An automated test fails the build if one appears.

                  No storage

                  Nothing is written to localStorage, cookies or IndexedDB. Close the tab and the log data, and your settings, are gone.

                  No telemetry

                  No analytics, tracking, advertising or error reporting. The page loads three local files and nothing else.

                  Disclaimer

                  Educational SOC triage tool. Findings indicate activity that may deserve investigation and do not prove malicious behaviour.

                  Only analyse logs from systems you own or are authorised to investigate.

                  What this tool cannot do

                  Knowing the limits of a tool is part of being a good analyst.

                  An event is not proof. Every finding is a reason to look further, never a verdict.
                  Absence of evidence is not evidence of absence. If auditing was switched off, those events do not exist in the export.
                  CSV exports differ between machines. Column names, date formats and encodings vary with Windows version and regional settings.
                  Not every event carries a source IP. Local and console logons legitimately have none.
                  No baselining. The tool cannot know whether a login is normal for you; only a human with context can decide that.
                  No cross-system correlation. It sees only the file you give it.
                  Timestamps can be ambiguous. Where day/month order is unclear, the tool says so and disables time-window rules rather than guessing.
                  Not an EDR, SIEM or SOC platform. It is a teaching aid for reading one export carefully.

                  Full detail, including export caveats and false-positive examples, is in README.md.
